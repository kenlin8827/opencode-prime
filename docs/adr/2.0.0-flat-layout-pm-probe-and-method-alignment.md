# 2.0.0 · Flat-layout PM probe with opencode-method alignment

> Supersedes the "package-manager fallback chain bun→pnpm→yarn→npm for plugin runtime deps" note in ADR-2.0.0 (typed-plugin-literals) More Information.

## Context and Problem Statement

OCP provisions TUI-plugin runtime deps (`@opentui/solid` pinned 0.5.10, strict peer `solid-js@1.9.12`) by merging `~/.config/opencode/package.json` and running a LOCAL package-manager install there. The TUI loader (opencode's embedded Bun runtime) resolves plugin bare `import()`s by walking root-level `node_modules`, which requires a FLAT layout; server plugins are unaffected (zero runtime bare imports, ADR-2.0.0 typed-plugin-literals). The previous chain probed `bun → pnpm → yarn → npm`, but pnpm's default isolated layout keeps auto-installed peers out of reach of plugin files (the root `node_modules/solid-js` marker never exists) — verified on a real machine that carried an orphan `pnpm-lock.yaml` with no `node_modules` at all, where `@opentui/solid/jsx-runtime` failed to resolve. An exit-0 install therefore did not imply a working tree, and a stray lockfile could anchor selection to the one PM class that breaks the loader. Separately, the global-install chain (`resolvePmForSpec`) uses opencode's own install method as a user-preference proxy; whether the local config-dir install should consult it was disputed.

## Decision Outcome

Chosen option: **layout-contract-first probe order with a filtered alignment head**.

1. Baseline order `bun → npm → yarn → pnpm` (`LOCAL_PM_ORDER`): the two flat-layout PMs lead; pnpm/yarn are demoted to last-resort fallbacks.
2. `localPmOrder(getInstallMethod())` may promote a detected `bun`/`npm` to the head (opencode install-method alignment), but detect values `pnpm`/`yarn`/`official`/`unknown` fall through to the baseline — alignment re-orders only WITHIN the flat pair and can never promote a layout the contract demotes. Chosen PM remains availability-gated by a real `<pm> --version` probe (path shape proves "installed once", not "runs now").
3. Correctness is verified on the RESULT side: `findMissingTuiDepMarkers` gates the fast path, and a zero-exit install whose markers are absent is reported as honest `failed (non-flat layout)` instead of a fake success.
4. Lockfiles are informational only: `LOCKFILE_OWNERS` never influences selection and foreign lockfiles are surfaced in the success message (`left untouched`), never deleted (cp-dataloss).

**Positive**: TUI plugin trees are resolvable by construction; preference alignment with opencode's install method is honored where it is safe; failures are self-describing and self-healing (manual `npm install` hint + persistent marker fast path).

**Negative / Risks**: yarn/berry-PnP and pnpm-only machines still attempt a last-resort install that re-check will flag (warning-only degradation, by design); an env-knob escape hatch (`OCP_PLUGIN_PM`) was explicitly deferred until real bun-network failure reports appear.

### Confirmation
