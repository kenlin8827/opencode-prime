# Iteration 0.41.0 · Major-version upgrade lock

> Index: [`README.md`](./README.md).

## Cheatsheet

1. `ocp update` / `ocp upgrade` refuse any upgrade that crosses the semver major boundary — for OCP itself and every companion tool (ADR-0.41.0#01)
2. The lock list is the registry itself: `update_policy.lock_major_default: true` in `install/tools.jsonc`; per-tool opt-out via `update_check.lock_major: false` (ADR-0.41.0#01)
3. OCP itself is always locked (not a registry entry); `--force` re-downloads/re-applies but never bypasses the lock (ADR-0.41.0#02)
4. Enforcement is six points deep: report partition + applier guard (`ocp update`); probe + archive-overlay + installer-apply guards (`ocp upgrade`) (ADR-0.41.0#02)
5. Tool upgrades re-verify the binary major after apply (TOCTOU guard): detect + warn with a pin-back hint, no rollback (ADR-0.41.0#03)
6. Escape hatch: `ocp init` + fresh install from the latest release one-liner (installer carries no lock) (ADR-0.41.0#04)

---

### 01. Lock the entire tool registry to its current major by default
**Status**: ✅ accepted

**Background**: `isNewerVersion` blocks only downgrades — a same-direction jump across majors (opencode 1.18.32 → 2.0.0, OCP 0.45.0 → 1.0.0) sailed through `ocp update` as an ordinary "update available" and through `ocp upgrade` as an ordinary overlay. Cross-major jumps are the one upgrade class that routinely breaks installed configs: template mergers, shipped-file layouts, and binary CLIs all assume same-major evolution.

**Decision**:

| # | Point | Content |
| --- | --- | --- |
| 1 | Lock list | The `tools` map in `install/tools.jsonc` IS the lock list — every declared tool (rtk, herdr, luvus, openchamber_web, tgrep, ripgrep, opencode) is locked by default, so newly added tools are locked without extra steps |
| 2 | Policy block | `update_policy.lock_major_default: true` (fail-closed: a missing block or a failed registry load leaves the lock ON via `policyDefaultFromRegistry`) |
| 3 | Opt-out | `"lock_major": false` inside a tool's `update_check` block; explicit `true` re-locks against an unlocked default (`majorLockEnabled`) |
| 4 | Unprovable input | `isCrossMajorVersion` returns false on NaN majors — the lock refuses only what it can prove; garbage versions fall through to the pre-existing `isNewerVersion` behavior |

**Rationale**:

- **Default-locked beats list-locked** — an explicit per-tool `lock_major: true` list silently leaves every future tool unlocked; fail-closed default makes forgetting impossible
- **No parallel list** — a second "locked tools" file would drift from the registry; the registry that drives updates also drives the lock
- **Fail-closed on unreadable input** — a missing registry/policy must not become a silent unlock

**Rejected**:

| Option | Reason rejected |
| --- | --- |
| Per-tool `lock_major: true` everywhere, default unlocked | Every new tool starts unlocked until someone remembers the flag — exactly backwards for a lock |
| Separate `locked_tools: [...]` list in tools.jsonc | Duplicates the registry; drifts on every add/remove/rename |
| Block only opencode + OCP by hardcoded names | Leaves rtk/herdr/luvus/openchamber/tgrep/ripgrep unguarded; hardcoding names outside the registry fights the registry-driven architecture |
| Fail-open on missing policy (lock only when explicitly configured) | A deleted or unparsable policy block would silently unlock the whole fleet |

**Impact**:

- **Installer** — `ToolRegistry` gains optional `update_policy`; `ToolEntryUpdate` gains optional `lock_major`
- **Updater** — `majorOf`/`isCrossMajorVersion` in manifest.ts (next to `isNewerVersion`); `isBlockedMajorUpgrade`/`majorLockEnabled`/`policyDefaultFromRegistry`/`shouldOverlayRelease`/`partitionUpdates` exported pure helpers in updater.ts
- **Tests** — 34 new truth-table assertions in `tests/test-updater-unit.ts` (42 total, incl. the 1.18.32→2.0.0 and 0.45.0→1.0.0 examples)
- **Docs** — `ocp-cli.md` EN+zh mirrors gain a Major-version lock section

### 02. OCP itself is always locked; `--force` never bypasses; six enforcement points
**Status**: ✅ accepted

**Background**: OCP is not a registry tool, so the registry policy cannot cover it; it needs an inherent lock. And the lock must survive the two entry paths (`ocp update`'s pending list, direct `ocp upgrade`) plus their degraded modes (blind download when the version probe fails on CN networks; repo copy advanced out-of-band via `git pull`).

**Decision**:

| # | Point | Content |
| --- | --- | --- |
| 1 | OCP lock | `majorLocked: true` hardcoded on the `ocp` ComponentCheck; `executeUpgrade` guards consult no registry state |
| 2 | `--force` scope | Re-download and re-apply only — all three `executeUpgrade` guards ignore `force` |
| 3 | Six points | `ocp update`: (a) `partitionUpdates` excludes blocked rows from pending and reports them; (b) `applyComponentUpgrade` defense-in-depth guard. `ocp upgrade`: (c) probe guard refuses before download; (d) overlay guard aborts on a cross-major archive (`shouldOverlayRelease`); (e) apply guard refuses installed-vs-repo cross-major in both directions; (f) tool-path TOCTOU verify (see 03) |
| 4 | Downgrades | Cross-major *downgrades* via `-f` are refused too — a cross-major apply in either direction is the jump the lock exists to prevent |

**Rationale**:

- **Each guard closes a real bypass**: direct `ocp upgrade` never passes through the update report; a failed probe forces a blind download whose major is only visible at overlay time; a `git pull` can advance the repo copy past the overlay guard entirely
- **`--force` stays a re-apply tool** — letting it bypass the lock would reduce the lock to a suggestion defeatable from the same command line

**Rejected**:

| Option | Reason rejected |
| --- | --- |
| Guard only the pending list | Direct `ocp upgrade` is a separate entry point with its own download/overlay/apply — unguarded |
| Allow `--force` to bypass | Force is for re-download/re-apply (stale mirror, half-applied overlay); conflating it with "break the lock" destroys the 限定死 guarantee |
| Block upgrades only, allow cross-major forced downgrades | A cross-major downgrade breaks configs just as badly (stale-file prune, template mergers); direction-agnostic refusal is simpler to explain |

**Impact**:

- **UX** — blocked updates print as a dedicated report section ("blocked by the major-version lock" + `vX → vY`); `--check-only` and non-TTY modes still surface them since the notice prints before the mode branches
- **Exit codes** — blocked applies return 1 with a message naming the escape hatch; the blocked-only update report still exits 0

### 03. TOCTOU post-upgrade verify for companion tools (detect + warn, no rollback)
**Status**: ✅ accepted

**Background**: The lock decision consumes the probe snapshot, but a tool upgrade runs `pkg@latest` or an official installer — whatever is newest AT APPLY TIME. A major published inside the probe→apply window (the interactive prompt can sit for minutes) slips past the pending filter.

**Decision**: After a successful tool upgrade (`code === 0`), `verifyPostUpgradeMajor` re-reads the binary's version via `localBinaryVersion` and, on a major crossing, prints a loud warning with a pin-back hint (`npm install -g <pkg>@<old>` when `upgrade_package` is known, else the tool's own installer). Detection only — no automatic rollback.

**Rationale**:

- **Prevention is impossible here** — script-based installers (`curl | sh`) cannot be pinned to a major; only the smart-strategy npm path could be, and diverging the two strategies breaks the uniform registry contract
- **Warning is honest** — the upgrade did happen; failing the run afterward would misreport, and silent rollback would fight the user's explicit upgrade intent

**Rejected**:

| Option | Reason rejected |
| --- | --- |
| Pin `pkg@<major>` at apply time | Requires resolving "latest same-major" via an extra registry query per tool, and is unimplementable for script installers — asymmetric complexity for a minutes-wide race |
| Auto-rollback on violation | Cannot roll back script installs; would also undo an upgrade the user explicitly confirmed |
| Accept the race silently | Violates the lock's stated guarantee for exactly the users who read the docs and trust it |

**Impact**:

- **Runtime** — one extra `--version` probe per successfully upgraded tool; zero network
- **Tests** — the decision (`isCrossMajorVersion`) is pinned; the IO wrapper is intentionally untested (same policy as other fs/network seams)

### 04. Escape hatch: `ocp init` + fresh install from the latest release
**Status**: ✅ accepted

**Background**: A lock with no documented exit is a trap. But the exit must stay a deliberate manual act — otherwise it becomes the bypass.

**Decision**: The documented vehicle is `ocp init` (backs up + clears the target, removing `installed.version`) followed by the README quick-install one-liner (POSIX `curl …/install.sh | bash`, Windows `irm …/install.ps1 | iex`), which downloads the newest release directly. The installer itself carries no lock; `ocp upgrade` / `ocp install` alone cannot do the jump (they work from the still-old-major local repo copy — a `git pull` first works too). Named explicitly in `ocp-cli.md` EN+zh so users never report the hatch as broken.

**Rationale**:

- **Deliberate-act bar** — re-running the one-liner is unambiguous user intent, unlike a flag on the same command that would erode the lock
- **Honest docs** — stating what does NOT work (`ocp upgrade` post-`init`) prevents the exact support ticket the hatch would otherwise generate

**Rejected**:

| Option | Reason rejected |
| --- | --- |
| A `--jump-major` / `--allow-major` flag | Puts the bypass on the same command line as the lock — the lock stops being 限定死 |
| Undocumented escape (fresh install works, docs silent) | Users file "lock cannot be bypassed" issues; the policy looks like a bug, not a decision |

**Impact**:

- **Docs** — EN+zh sections updated; release notes (`install/versions/0.41.0.notes.md`) repeat the hatch

**Future extensions**: per-tool `lock_major: false` for tools whose upstream crosses majors routinely (ripgrep 14→15 is the current candidate) if the pinned-until-manual posture proves too conservative in practice.
