# Iteration 0.41.0 · 大版本升级锁

> 索引：[`README.md`](./README.md)。

## 速查表

1. `ocp update` / `ocp upgrade` 拒绝一切跨 semver 大版本号的升级——套件本体与所有配套工具一律如此（ADR-0.41.0#01）
2. 锁清单就是注册表本身：`install/tools.jsonc` 中的 `update_policy.lock_major_default: true`；个别工具用 `update_check.lock_major: false` 豁免（ADR-0.41.0#01）
3. OCP 本体恒定锁死（不是注册表条目）；`--force` 只管重新下载/重新应用，绝不能绕过锁（ADR-0.41.0#02）
4. 六处纵深执行：报告分区 + 应用守卫（`ocp update`）；探测守卫 + 发布包覆盖守卫 + 安装器应用守卫（`ocp upgrade`）（ADR-0.41.0#02）
5. 工具升级后复验二进制大版本（TOCTOU 守卫）：只检测告警并给出回 pin 提示，不自动回滚（ADR-0.41.0#03）
6. 逃生舱：`ocp init` + 用最新发布包的一键安装命令全新安装（安装器本身不带锁）（ADR-0.41.0#04）

### 01. 整个工具注册表默认锁定在当前大版本
**状态**：✅ accepted

**背景**：`isNewerVersion` 只拦截降级——同方向的跨大版本跳跃（opencode 1.18.32 → 2.0.0、OCP 0.45.0 → 1.0.0）会作为普通 "update available" 通过 `ocp update`，作为普通覆盖通过 `ocp upgrade`。跨大版本是唯一经常破坏已安装配置的升级类别：模板合并、发布文件布局、二进制 CLI 都假设同大版本演进。

**决策**：

| # | 要点 | 内容 |
| --- | --- | --- |
| 1 | 锁清单 | `install/tools.jsonc` 的 `tools` 映射本身就是锁清单——其中声明的每个工具（rtk、herdr、luvus、openchamber_web、tgrep、ripgrep、opencode）默认全部锁死，新增工具无需额外步骤即被锁定 |
| 2 | 策略块 | `update_policy.lock_major_default: true`（fail-closed：策略块缺失或注册表加载失败时 `policyDefaultFromRegistry` 仍保持锁定） |
| 3 | 豁免 | 工具的 `update_check` 块中写 `"lock_major": false`；显式 `true` 可对抗已解锁的默认值（`majorLockEnabled`） |
| 4 | 不可判定输入 | `isCrossMajorVersion` 对 NaN 大版本返回 false——锁只拒绝能证明的跨越；垃圾版本号回退到既有 `isNewerVersion` 行为 |

**依据**：

- **默认锁定胜过清单锁定**——逐工具 `lock_major: true` 的显式清单会让每个新增工具在有人记得加标记之前处于未锁定状态，与锁的初衷正好相反
- **不维护第二份平行清单**——另一份 "locked tools" 文件会在每次增删改名时与注册表漂移；驱动更新的注册表同时驱动锁
- **不可读输入下 fail-closed**——缺失的注册表/策略块绝不能成为静默解锁

**否决**：

| 方案 | 否决理由 |
| --- | --- |
| 全工具写 `lock_major: true`、默认不锁 | 每个新工具在有人记得加标记前都是未锁定的——锁机制倒置 |
| tools.jsonc 里另起 `locked_tools: [...]` 清单 | 与注册表重复；每次增删改名都会漂移 |
| 只硬编码 opencode + OCP 两个名字 | rtk/herdr/luvus/openchamber/tgrep/ripgrep 全部失守；注册表外硬编码名字与注册表驱动架构相悖 |
| 策略缺失时 fail-open（只显式配置才锁） | 删除或损坏策略块会静默解锁整个工具群 |

**影响**：

- **安装器**——`ToolRegistry` 新增可选 `update_policy`；`ToolEntryUpdate` 新增可选 `lock_major`
- **更新器**——`majorOf`/`isCrossMajorVersion` 放在 manifest.ts（紧邻 `isNewerVersion`）；`isBlockedMajorUpgrade`/`majorLockEnabled`/`policyDefaultFromRegistry`/`shouldOverlayRelease`/`partitionUpdates` 作为可导出纯函数放在 updater.ts
- **测试**——`tests/test-updater-unit.ts` 新增 34 条真值表断言（共 42 条，含 1.18.32→2.0.0 与 0.45.0→1.0.0 两个实例）
- **文档**——`ocp-cli.md` 中英镜像新增大版本锁章节

### 02. OCP 本体恒定锁死；`--force` 永不绕过；六处执行点
**状态**：✅ accepted

**背景**：OCP 不是注册表工具，注册表策略覆盖不到它，需要内在锁死。且锁必须经受两条入口（`ocp update` 的待办列表、直达的 `ocp upgrade`）及其降级模式：CN 网络下版本探测失败时的盲下载、经 `git pull` 带外推进的 repo 副本。

**决策**：

| # | 要点 | 内容 |
| --- | --- | --- |
| 1 | OCP 锁 | `ocp` ComponentCheck 上硬编码 `majorLocked: true`；`executeUpgrade` 的守卫不查任何注册表状态 |
| 2 | `--force` 范围 | 只管重新下载与重新应用——`executeUpgrade` 的三个守卫全部无视 `force` |
| 3 | 六处执行点 | `ocp update`：(a) `partitionUpdates` 把拦截项排除出 pending 并单独报告；(b) `applyComponentUpgrade` 纵深守卫。`ocp upgrade`：(c) 探测守卫在下载前拒绝；(d) 覆盖守卫对跨大版本发布包中止（`shouldOverlayRelease`）；(e) 应用守卫双向拒绝 installed-vs-repo 跨大版本；(f) 工具链 TOCTOU 复验（见 03） |
| 4 | 降级 | `-f` 的跨大版本**降级**同样拒绝——任一方向的跨大版本应用正是锁要阻止的跳跃 |

**依据**：

- **每个守卫都堵一条真实旁路**：直达 `ocp upgrade` 不经过更新报告；探测失败被迫盲下载时，大版本跳跃要到覆盖层才可见；`git pull` 可把 repo 副本直接推过覆盖守卫
- **`--force` 保持为重放工具**——允许它绕过锁，等于把锁降格为同一命令行上可破除的建议

**否决**：

| 方案 | 否决理由 |
| --- | --- |
| 只守待办列表 | 直达 `ocp upgrade` 是独立入口，自带下载/覆盖/应用——全程失守 |
| 允许 `--force` 绕过 | force 用于重下载/重放（镜像滞后、覆盖中断）；把它和"破锁"混为一谈，锁的限定死保证即破 |
| 只拦升级、放行 `-f` 跨大版本降级 | 跨大版本降级同样破坏配置（陈旧文件裁剪、模板合并）；双向拒绝更简单、更好解释 |

**影响**：

- **交互**——拦截项以独立报告节呈现（"blocked by the major-version lock" + `vX → vY`）；通知打印在模式分支之前，`--check-only` 与非 TTY 同样可见
- **退出码**——被拦的应用返回 1 并指明逃生舱；纯拦截的更新报告仍返回 0

### 03. 配套工具 TOCTOU 升级后复验（只检测告警，不回滚）
**状态**：✅ accepted

**背景**：锁的决策消费的是探测快照，而工具升级执行的是 `pkg@latest` 或官方安装器——即**应用时刻**的最新版。探测→应用窗口内（交互确认可悬置数分钟）发布的新大版本会穿过待办过滤。

**决策**：工具升级成功后（`code === 0`），`verifyPostUpgradeMajor` 经 `localBinaryVersion` 重读二进制版本，发生大版本穿越即大声告警并给出回 pin 提示（`upgrade_package` 已知时为 `npm install -g <pkg>@<旧版>`，否则用工具自带安装器）。只检测，不自动回滚。

**依据**：

- **此处无法预防**——脚本类安装器（`curl | sh`）不能 pin 大版本；只有 smart 策略的 npm 路径可以，分岔两种策略会破坏统一的注册表契约
- **告警是诚实的**——升级确实发生了；事后报失败是误报，静默回滚则与用户显式确认的升级意图相悖

**否决**：

| 方案 | 否决理由 |
| --- | --- |
| 应用时刻 pin `pkg@<大版本>` | 需为每个工具多一次注册表查询以解析"同大版本最新"，且脚本安装器根本做不到——为数分钟宽的竞态付出不对称复杂度 |
| 越界自动回滚 | 脚本安装无法回滚；还会撤销用户显式确认的升级 |
| 静默接受竞态 | 违背锁对读过文档并信任它的用户的明示保证 |

**影响**：

- **运行时**——每个成功升级的工具多一次 `--version` 探测；零网络
- **测试**——决策层（`isCrossMajorVersion`）已钉死；IO 包装层按惯例不测（与其他 fs/网络缝隙同等对待）

### 04. 逃生舱：`ocp init` + 从最新发布包全新安装
**状态**：✅ accepted

**背景**：没有书面出口的锁是陷阱。但出口必须保持为刻意的手动行为——否则它就成了旁路。

**决策**：书面载体为 `ocp init`（备份并清空目标，移除 `installed.version`）+ 执行 README 一键安装命令（POSIX 为 `curl …/install.sh | bash`，Windows 为 `irm …/install.ps1 | iex`），直接下载最新发布包。安装器本身不带锁；单独的 `ocp upgrade` / `ocp install` 无法完成跨越（它们基于仍在旧大版本的本地 repo 副本；先 `git pull` 亦可）。在 `ocp-cli.md` 中英镜像中点名，以免用户误报逃生舱损坏。

**依据**：

- **刻意行为门槛**——重跑一键安装是无歧义的用户意图；同一命令上的开关会侵蚀锁
- **诚实文档**——写明什么**不行**（`init` 之后 `ocp upgrade` 仍被拦）才能避免逃生舱必然引发的支持工单

**否决**：

| 方案 | 否决理由 |
| --- | --- |
| `--jump-major` / `--allow-major` 开关 | 把旁路放在与锁同一命令行上——锁不再是限定死 |
| 不写文档（全新安装本来就行，文档保持沉默） | 用户会提交"锁无法绕过" issue；策略看起来像 bug 而非决策 |

**影响**：

- **文档**——中英章节已更新；发布说明（`install/versions/0.41.0.notes.md`）重复逃生舱

**后续扩展**：若"pin 住等手动"对上游常规跨大版本的工具（当前候选 ripgrep 14→15）过于保守，可为其加 `lock_major: false`。

### 05. 后续：全新安装锁 + opencode v1 钉死
**状态**：✅ 已接受

**背景**：§04 把 `ocp install` 故意留作无锁逃生口——但用大版本不一致的 repo 副本裸跑 `ocp install` 会静默跨大版本回退（或前进），等于用最常用的命令绕开锁。另外所有 opencode 安装路径都委托给官方 "latest" 一键脚本，v2 发布那天它就会交出 v2——而 OCP 插件/SDK 只认 v1。

**决策**：

| # | 要点 | 内容 |
| --- | --- | --- |
| 1 | 全新安装锁 | `executeInstall` 在备份/变更之前双向拒绝已装-vs-仓库的跨大版本应用（`isBlockedFreshInstall`）；`--force` 永不绕过；§04 逃生口收窄为 `ocp init` + 一键安装命令 |
| 2 | opencode v1 钉死 | `install/tools.jsonc` 的 opencode 安装/升级改为 `@script:opencode`（POSIX 用 `install/scripts/tools/opencode.sh`，Windows 用 `opencode.ps1`，全平台矩阵均可解析）；脚本只装最新 *v1* 发布包，PATH 上有 v2+ 二进制直接拒绝（exit 1，绝不覆盖/遮蔽），装完再验一次大版本 |
| 3 | 引导器与 provision 守卫 | `install/install.sh\|.ps1` 的 opencode 自动安装委托给同一个钉死脚本（官方 `install.ps1` 端点 HTTP 404，Windows 改为直下发布包）；`provisionTools` 拒绝 PATH 上的 v2，v2 存在期间跳过所有依赖 opencode 的 post-install 步骤 |
| 4 | 不可证输入 | 与 §01 同样的 fail-open 哲学：缺失/不可解析的版本永不拦截 |
